# Подтверждение почты при регистрации — проект

2026-09-14. Первая часть более крупной инициативы (сброс пароля через почту,
роль «организатор» с одобрением — отдельные спеки позже, обе лягут на ту же
email-инфраструктуру, которую строит эта).

## Задача

При регистрации почта уже обязательна (`RegisterRequest.email: EmailStr`), но
никак не проверяется — ввести чужой/несуществующий адрес ничего не мешает.
Нужно письмо со ссылкой подтверждения, статус в `/users/me`, и ненавязчивое
напоминание, пока почта не подтверждена.

## Канонический auth-стек

В проекте раньше было два параллельных auth-модуля (`app/modules/auth/` и
`app/modules/identity/`) — см. `CLAUDE.md`. Начиная с `aa0b8b8` это больше не
так: `identity`'s собственные `/register`/`/login` удалены как мёртвый код,
`auth` — единственный работающий стек, сессии — httpOnly-куки
(`app/core/session_auth.py`), `/users/me` живёт в `auth/router.py`, читая
данные из `identity`'s `AuthService.get_user_me` без дублирования. Всё ниже
строится на `auth`. `CLAUDE.md`'s раздел про дублирование теперь устарел и
должен быть обновлён отдельным PR.

## Email-инфраструктура (переиспользуемая)

Новый `app/core/email.py` — обёртка над Resend (`resend` в
`requirements.txt`). Настройки в `config.py`:

* `resend_api_key: str | None` — не задан по умолчанию;
* `email_from: str` — например `"Мстинская традиция <noreply@домен>"`;
* `frontend_base_url: str` — для построения ссылок в письмах (сейчас такого
  поля нет, добавляется этой задачей).

Если `resend_api_key` не задан (dev/test по умолчанию), сервис не делает
реальный сетевой вызов — логирует тему и ссылку. Ни локальная разработка, ни
тесты не требуют настоящего ключа. Домен под Resend пользователь верифицирует
сам (DNS-записи); без этого письма реально доходят только до e-mail
владельца аккаунта Resend — это операционный шаг вне кода.

Сервис пишется один раз и переиспользуется сбросом пароля и одобрением
организатора, когда до них дойдёт очередь.

## Данные

Миграция Alembic добавляет:

* `users.email_verified_at: datetime | None`, `NULL` по умолчанию —
  подтверждена ли почта и когда.
* Новая таблица `email_verification_tokens`:
  `id`, `user_id`, `token_hash`, `expires_at`, `used_at: datetime | None`.

Токен — `secrets.token_urlsafe(32)`, в письмо идёт сырой токен, в базе —
только его хеш (тот же принцип, что и у refresh-токенов: секрет не лежит в
БД в открытом виде). Срок жизни — 24 часа.

## Поток

1. `POST /api/v1/auth/register` создаёт пользователя и коммитит, как сейчас.
   После коммита — генерирует токен, сохраняет его хеш, вызывает
   `EmailService.send_verification_email(user, token)`. Сбой отправки
   (Resend недоступен) **не** проваливает регистрацию — только логируется;
   пользователь всегда может запросить письмо повторно.
2. Письмо содержит ссылку `{frontend_base_url}/verify-email?token=<raw>`.
3. Пользователь кликает → фронтенд-страница `verify-email` (клиентский
   компонент) читает `token` из query, шлёт `POST /api/v1/auth/verify-email
   {token}` → бэкенд ищет токен по хешу, проверяет `expires_at`/`used_at`,
   ставит `users.email_verified_at = now()`, помечает токен использованным.
4. `GET /api/v1/auth/users/me` (`UserMeResponse`) получает новое поле
   `email_verified: bool` — по нему UI решает, показывать ли напоминание.

Регистрация продолжает сразу заводить сессию (как сейчас) — вход не
блокируется отсутствием подтверждения. Отвергнутый вариант: блокировать вход
до подтверждения — надёжнее против фейковых email, но добавляет трение в
регистрацию без выигрыша, оправданного масштабом сообщества.

## Эндпоинты

`app/modules/auth/router.py`:

* `POST /api/v1/auth/verify-email {token}` → `MessageResponse`.
  Ошибки: `400` — невалиден или уже использован; `410` — истёк срок.
* `POST /api/v1/auth/resend-verification` — требует активной сессии (текущий
  пользователь из `get_session_user`). Если `email_verified_at` уже
  установлен — no-op, `MessageResponse` без повторной отправки. Иначе
  инвалидирует предыдущий неиспользованный токен пользователя (если был),
  создаёт новый, шлёт письмо повторно. `@limiter.limit("3/hour")` — тот же
  `slowapi`-лимитер, что уже используют `/register`/`/login`.

## Фронтенд

* `frontend/src/app/verify-email/page.tsx` — клиентский компонент. Читает
  `token` из `useSearchParams`, шлёт запрос при монтировании, показывает один
  из трёх исходов: успех (+ ссылка на главную/профиль), невалиден, истёк (+
  кнопка «отправить письмо ещё раз», если пользователь залогинен).
* Баннер-напоминание — рядом с текущим пользователем в хедере (около
  `AccountAction`/`site-header.tsx`), рендерится только когда
  `user && !user.emailVerified`. Кнопка «Отправить письмо ещё раз» →
  `resend-verification`.
* Клиентский кулдаун на этой кнопке (и на кнопке на странице `verify-email`):
  после клика кнопка неактивна `60` секунд с обратным отсчётом, локальный
  `useState`/`setInterval`, без персистентности между перезагрузками страницы.
  Это не защита (её обеспечивает серверный rate-limit), а просто не даёт
  кликать подряд по невнимательности.

## Тестирование

* Бэкенд: `backend/tests/test_email_verification_api.py`, по образцу
  существующих (`sqlite+aiosqlite` в памяти, `fastapi.testclient.TestClient`).
  `EmailService` в тестах подменяется (monkeypatch/фейковый sender) —
  никаких настоящих сетевых вызовов; токен для последующей проверки эндпоинта
  берётся из перехваченного вызова, а не читается из БД в открытом виде (в
  БД лежит только хеш).
  Сценарии: успешная регистрация шлёт письмо → verify-email с валидным
  токеном подтверждает → повторное использование того же токена даёт `400` →
  истёкший токен даёт `410` → resend-verification создаёт новый рабочий
  токен и инвалидирует старый → rate-limit на resend отдаёт `429` после
  превышения.
* Фронтенд: инфраструктуры для автотестов сейчас в проекте нет — страница
  `verify-email` и баннер проверяются вручную через dev-сервер (успех/ошибка/
  истёк/кулдаун).

## Не входит в эту задачу

* Сброс пароля через почту — отдельная спека, переиспользует
  `app/core/email.py`.
* Роль «организатор» и одобрение регистрации — отдельная спека.
* Блокировка входа до подтверждения — сознательно не делается (см. «Поток»).
* Обновление `CLAUDE.md`'s раздела про дублирование auth-стеков.
