# Реорганизация главной страницы: разделение "лендинга" и функциональных разделов

Date: 2026-09-03

## Проблема

Главная страница (`frontend/src/app/page.tsx`) на текущий момент содержит почти весь контент платформы одним длинным скроллом: Hero, живую афишу турниров, историю (Буза, Стенка/Круг), интерактивное демо-прохождение турнира (Поединок → Сетка → Правила-квиз → Бойцы), Снаряжение, Архив экипировки, Хронику и Живопись, закрытое якорным оглавлением `SectionIndex` (8 пунктов).

Параллельно шапка (`SiteHeader`) ведёт на тонкие реальные подстраницы: `/tournaments`, `/athletes`, `/clubs`, `/rules`, `/education`. Часть из них (`/tournaments`, `/rules`) уже реальны и управляются настоящими данными, но дублируют по смыслу разделы на главной под похожими именами (Поединок/Сетка vs `/tournaments`; Правила-квиз vs `/rules`), что создаёт путаницу — фактически на сайте два параллельных источника контента по одной теме.

## Целевая структура

**Главная (`/`) — чистый лендинг:**
1. Hero (без изменений)
2. Живая афиша турниров (`Ближайшие турниры`, реальные данные, ссылка на `/tournaments`) — без изменений
3. Буза (история/лор, свёрнута по умолчанию) — без изменений. Явно помечена в коде как non-authoritative scene-setting, не регламент — уместна только как атмосферный контент витрины.
4. Стенка/Круг (иллюстративный сторителлинг форматов) — без изменений, той же природы, что и Буза.
5. Хроника + Живопись (закрывающая архивная галерея) — без изменений.
6. `SectionIndex` — **удаляется**. После переноса демо-блока на главной остаётся 2 содержательных раздела (Хроника, Живопись) — якорное оглавление на 2 пункта избыточно.

**`/tournaments` — реальный список турниров + демо-блок "Как проходит турнир":**
- Существующий реальный список турниров (`TournamentsPage`) остаётся без изменений и идёт первым — это функциональное назначение страницы.
- Ниже добавляется перенесённый блок: Поединок → Сетка → Правила (квиз) → Бойцы, обёрнутый в тот же `TournamentPathProvider` (у них общий стейт "заявленный разряд" и общий фиксированный демо-датасет `bracket-data.ts` — переезжают только вместе).
- `RulesQuiz` — не выдумка, контент уже сверен с первоисточником (buza.su, см. комментарий в `rules-quiz.tsx`). Дублировать текст реальных правил в `/rules` он не должен — вместо этого получает ссылку-переход "Полный регламент →" на настоящую `/rules`.
- `Dossiers` (Бойцы) остаются при демо-блоке, а не переезжают в `/athletes`: это фиксированные демо-бойцы из `bracket-data.ts`, не настоящие карточки атлетов — смешивать их с реальным ростером было бы некорректно.

**Новая страница `/equipment`:**
- Переносятся `Equipment` (Снаряжение — 4 разряда лота, реальные данные `getBoutRules()`) и `GearArchive` (Архив экипировки — 9 предметов опис).
- Название маршрута совпадает с уже объявленным в `CLAUDE.md` backend-доменом `equipment`, для которого сейчас нет фронтенд-роута.

**Шапка (`SiteHeader`):**
- Новый пункт `NAV`: `{ href: "/equipment", label: "Снаряжение" }`.
- Итоговый порядок: Турниры · Спортсмены · Клубы · Правила · Снаряжение · Обучение.
- Требует записи в `NAV_WEAPON` (мотив для dice-flip реверса пункта меню) — выбрать неиспользованный ещё мотив по аналогии с существующими.

## Что не меняется

- Backend не затрагивается вообще — это чисто фронтенд-реорганизация существующих клиентских компонентов между роутами.
- `directory-index.tsx` (упомянутый в комментарии `page.tsx` как оставленный, но не рендерящийся) не трогаем.
- Данные и API-вызовы (`listTournaments`, `getBoutRules`) переезжают вместе с компонентами, которые их используют — без изменений контракта.

## Порядок реализации (поэтапно, не одним PR)

Компоненты трогаются целыми блоками, каждый этап — самостоятельный, проверяемый шаг:

1. **Этап 1** — перенос демо-блока (Поединок/Сетка/Правила-квиз/Бойцы) с `TournamentPathProvider` из `page.tsx` в `frontend/src/app/tournaments/page.tsx`, под реальным списком турниров. Добавить ссылку из квиза на `/rules`.
2. **Этап 2** — создание `frontend/src/app/equipment/page.tsx`, перенос `Equipment` + `GearArchive` туда. Добавление пункта "Снаряжение" в `SiteHeader` (`NAV` + `NAV_WEAPON`).
3. **Этап 3** — финальная чистка главной: удаление `SectionIndex` и его импорта/рендера из `page.tsx`, проверка что ничего больше не ссылается на снятые якоря (`#poedinok`, `#setka`, `#snaryazhenie`, `#arhiv-ekipirovki`, `#pravila`, `#bojcy`) — включая `RiverStrip`/другие компоненты, если они на них ссылаются.

После каждого этапа — визуальная проверка в dev-сервере (`npm run dev`) и `npx tsc --noEmit`.

## Риски / что проверить отдельно

- GSAP `ScrollTrigger` в `BracketConnector` триггерится по позиции скролла — при переезде на новую страницу нужно перепроверить, что анимация первого входа в область видимости всё ещё работает корректно (та же логика `once: true` должна работать одинаково на любой странице).
- Проверено: якорные ссылки (`#poedinok`, `#setka`, `#snaryazhenie`, `#arhiv-ekipirovki`, `#pravila`, `#bojcy`, `#hronika`, `#zhivopis`) используются только внутри `section-index.tsx` — больше нигде в кодовой базе на них не ссылаются, удалять `SectionIndex` на этапе 3 безопасно.
